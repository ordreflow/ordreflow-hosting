# OrdreFlow Kubernetes profiles

The shared manifests are in [`apps/ordreflow`](apps/ordreflow). The [dev overlay](overlays/dev/kustomization.yaml) runs on single-node Hetzner K3s, while the [local overlay](overlays/local/README.md) runs on k3d with locally built images and no Flux. Both reuse K3s Traefik and local-path storage.

The [K3s Terraform environment](../terraform/environments/k3s-test/README.md) provisions the server and DNS, creates the application secret, registers a GitHub deploy key, bootstraps Flux, and waits for the dev app to become healthy. A single `terraform apply` completes the deployment once the cloud and GitHub credentials are in the environment. The application hostname and Let's Encrypt contact email are supplied through Terraform and a `flux-system/k3s-test-settings` ConfigMap rather than edited into Git. The public GHCR images are pulled without registry credentials.

Flux watches `main` at `k8s/clusters/test`. Backend and frontend CI publish `:dev` images after successful builds on the `dev` branch. The backend pushes API before migrations. Flux watches the **migrations `:dev` digest** as the backend release signal, updates a pod-template annotation in the [dev overlay](overlays/dev), and Kubernetes pulls both `:dev` images when it restarts the API. Frontend updates use its own `:dev` digest. CI still publishes `:main` images, but this cluster intentionally follows `:dev`.

After apply, check `terraform -chdir=terraform/environments/k3s-test output -raw url`. For in-cluster debugging, use SSH and `k3s kubectl get pods -A`; `flux get kustomizations` and `flux get images all` are available on the server. The application bootstraps one administrator; demo employees are not seeded on K3s. PostgreSQL uses storage local to this VPS, so back up its data before replacing the server.
